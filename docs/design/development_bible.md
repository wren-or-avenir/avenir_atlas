# 开发工作流

本文件只定义 Avenir Atlas 的日常开发流程。架构、视觉和内容决策分别以 [structure.md](structure.md)、[visual_design.md](visual_design.md) 和 [content.md](content.md) 为准。

## 1. 明确范围

1. 从用户请求确定可验收结果；低风险、可逆细节自行决定。
2. 只读取与改动相关的代码、调用方和上述来源文档。
3. 用 `git diff` / `git status` 识别并保留无关的现有改动。
4. 只有会改变结果方向、需要新增权限或难以撤销时才提问；等待回复期间继续不依赖答案的工作。

## 2. 实现

- 先复用现有代码、浏览器/Astro 能力和已安装依赖，再考虑新增代码或依赖。
- 修复共享根因，不在每个调用方重复打补丁。
- 遵守 `pages → components → core` 依赖方向；Provider 契约只用于需要替换外部数据源的模块，具体边界见 `structure.md`。
- 不为假设中的未来需求添加接口、配置、状态机或目录。
- 错误处理与真实风险匹配：外部输入需校验；可恢复故障明确降级或报错；不得静默吞掉会导致数据丢失或错误状态的异常。
- 注释解释原因和约束，不复述代码。

## 3. 验证

按改动范围选择最小且有意义的检查：

| 改动 | 默认检查 |
| --- | --- |
| 文档或静态配置 | 审查 diff、路径、命令和链接 |
| 纯逻辑或行为 | `npm test`，必要时增加一个聚焦测试 |
| TypeScript / Astro 组件 | `npm run typecheck` |
| 构建、路由、资源或跨模块改动 | `npm run build` |
| 视觉或交互 | 后台启动 Astro，检查目标页面和浏览器错误 |

检查已通过且没有新增风险时停止；不要无理由重复或扩大测试。

## 4. 调试

1. 复现症状并收集最小证据。
2. 搜索相关实现与所有调用方，定位根因。
3. 用户要求诊断时只报告证据和结论；要求修复时直接实现并验证。
4. 仅在用户要求记录时新增 bug 文档；仅在真实取舍影响结果时提供方案选择。

调试服务器与已知 WebGL 问题见 [`docs/startup/debug.md`](../startup/debug.md)。

## 5. 完成

- 检查最终 diff，确认没有修改无关文件或泄露密钥。
- 行为、架构或操作方式发生变化时更新对应来源文档；不要复制同一规则到多处。
- 简要报告结果、修改文件、验证命令和未解决事项。
- 除非用户明确要求，不创建分支、提交、标签或发布。
